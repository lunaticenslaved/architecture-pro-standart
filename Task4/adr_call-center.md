### <a name="_qmphm5d6rvi3"></a>**Решение**

- [Диаграмма контекстов](./Context.png)
- [Диаграмма контейнеров](./Container.png)

#### Архитектурный подход:

- Для внутреннего кол-центра: сервер системы кол-центра обращается за ставками синхронными запросами
- Для партнёрского кол-центра: выгружать ставки единым файлом на сервер партнёра.

#### Обоснование

Данное решение учитывает ограничение партнёра и обеспечивает оптимальный UX для внутреннего кол-центра.

#### Технологический выбор

Используются те же компоненты и технологии, что и для предыдущего решения. Потребуется настроить выгрузку по cron в Rate Service.

#### Интеграции

##### Синхронные:

- Система кол-центра -> Rate Service (REST API)

##### Асинхронные:

Rate Export Service -> SFTP сервер партнёра (1 раза в день)

#### Безопасность

- REST API защищён OAuth 2.0 + JWT
- SFTP с SSH-ключами (публичный/приватный)
- Rate limiting на API endpoints


### <a name="_bjrr7veeh80c"></a>**Альтернативы**


#### Вариант 1: Создать VPN-туннель для сихронных запросов со стороны партнёрского кол-центра

##### Плюсы:

- Быстрое получание изменения ставок

##### Минусы:

- Партнёр не поддержит такое решение
- Долгое согласование со стороны службы безопасности

##### Вердикт:

Отклонено из-за ограничений партнёра.


#### Вариант 2: Использование единой БД

##### Плюсы:

- Быстрый доступ к изменениям

##### Минусы:

- Партнёр не поддержит такое решение
- Долгое согласование со стороны службы безопасности
- Риски безопасности

##### Вердикт:

Отклонено из-за ограничений партнёра и по соображениям безопасности.


### Недостатки, ограничения, риски

#### Недостатки решения

1. Ставки у партнёра обновляются только 1 раз в день
2. Риски недоступности SFTP-сервера
3. Зависимость от инфраструктуры партнёра

#### Ограничения

1. Фиксированный формат файла, что затрудняет интеграцию изменений при их необходимости
2. Партнёр не видит специальные предложения для клиента, только базовые ставки

#### Риски

1. Партнёр будет недобросовестно обслуживать SFTP-сервер
2. Партнёр будет недобросовестно заносить новые данные в свою систему
3. Утечка файлов

#### План снижения рисков

1. Предварительния интеграция с партнёром и тестирование
2. Периодическая оценка системы со стороны безопасности банка
3. Заключение NDA в партнёром
4. Использовать защищённого SSH-соединения, применение ширования.
